## 1. 当前架构

### 1.1 运行拓扑

```text
用户浏览器
┌──────────────────────────────────────────┐
│ index.html                               │
│                                          │
│  游戏逻辑 ──────────► localStorage       │
│     │                  ├─ dieshan.best.v1│
│     │                  └─ dieshan.size.v1│
│     └─ 无 fetch / XHR / WebSocket        │
└──────────────────────────────────────────┘

可选：任意静态文件服务器仅负责返回 index.html，
不参与游戏逻辑、不保存成绩、不接收对局数据。
```

### 1.2 无后端的设计选择

选择纯前端交付的原因：

1. 游戏为单人本地体验，无多人同步需求；
2. 不需要注册和登录，降低使用门槛；
3. 无服务器成本和数据库运维负担；
4. 离线可玩、跨网络可用；
5. 没有用户数据离开设备，隐私边界简单；
6. 单文件即可归档、复制和分享。

### 1.3 当前不存在的后端能力

以下能力在 0.1.0 中**均未实现**：

- REST / GraphQL API；
- 用户账户、登录、Token；
- 在线排行榜；
- 云端最佳成绩；
- 多人对战；
- 每日挑战的服务器种子；
- 服务端对局回放或防作弊；
- 数据统计、埋点或广告；
- 文件上传；
- 推送、邮件或消息服务。

## 2. 本地数据层

### 2.1 存储方式

使用浏览器标准 `localStorage`，它具备以下特性：

- 按 **源（origin）** 隔离：`https://example.com` 与 `http://localhost:8080` 不共享；
- 持久保存，直到用户或浏览器主动清除；
- 仅支持字符串键值；
- 同步 API；
- 常见浏览器配额约为 5 MB 级别，本项目数据量极小；
- 在隐私模式、禁用存储、存储配额耗尽或某些文件协议环境中，写入可能失败。

页面打开时读取偏好，成绩刷新时写入。

### 2.2 存储键定义

#### `dieshan.best.v1`

保存两种棋盘的独立最佳分数。

```json
{
  "4": 4864,
  "5": 2136
}
```

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `4` | number | 4 × 4 棋盘历史最高分，非负整数 |
| `5` | number | 5 × 5 棋盘历史最高分，非负整数 |

实现细节：

- 值以 JSON 字符串写入；
- 读取时对 `JSON.parse` 使用 `try / catch`；
- 只接受有限、非负数值，并向下取整；
- 缺失的尺寸回退为 `0`；
- 数据结构不包含玩家身份、时间戳或对局历史。

#### `dieshan.size.v1`

保存最近选择过的棋盘尺寸。

```text
"4" | "5"
```

- 浏览器存储的是字符串；
- 读取时用 `Number.parseInt` 并仅接受 4 或 5；
- 非法值回退到默认 `4`；
- 在用户切换棋盘尺寸时更新。

### 2.3 读写流程

```text
应用启动
   │
   ├─ 读取 dieshan.size.v1
   │     ├─ 合法 4 / 5 → 采用
   │     └─ 非法 / 不存在 → 使用 4
   │
   ├─ 读取 dieshan.best.v1
   │     ├─ JSON 合法 → 校验各尺寸数值
   │     └─ JSON 异常 → 最佳成绩均为 0
   │
   └─ 初始界面渲染

游戏中分数超过最佳成绩
   │
   ├─ 更新内存 state.bests[size]
   ├─ 更新页面数字
   └─ 尝试写入 dieshan.best.v1
         └─ 失败：不中断游戏，仅本次会话有效

切换尺寸
   │
   ├─ 写入 dieshan.size.v1
   └─ 重置对局使用新棋盘
```

### 2.4 容错策略

`readPreferences()` / `savePreferences()` 被 `try / catch` 包裹：

- 读取异常时使用默认值；
- 写入异常时静默降级；
- `JSON.parse` 失败不会导致页面崩溃；
- 不依赖本地存储完成核心玩法。

这样做的原因是：本地存储不是游戏运行的必要条件，不应因为浏览器安全策略影响可玩性。

### 2.5 清除数据

玩家可以通过浏览器开发者工具或站点设置清除本地数据。JavaScript 控制台命令示例：

```js
localStorage.removeItem("dieshan.best.v1");
localStorage.removeItem("dieshan.size.v1");
```

清除后刷新页面：

- 最佳成绩恢复为 `0`；
- 棋盘恢复到默认 `4 × 4`；
- 当前是否正在对局不会保存，因此始终从新局开始。

### 2.6 文件协议注意事项

直接以 `file://` 打开时，`localStorage` 的行为取决于浏览器：

- 某些浏览器允许同一文件路径共享本地存储；
- 某些浏览器会隔离、拒绝写入或在移动文件后丢失数据；
- 依赖 `try / catch`，游戏本身不会报错；
- 如需稳定的最佳成绩持久化，建议通过 HTTP(S) 静态服务器访问。

### 2.7 多标签页行为

当前实现**不监听** `storage` 事件，也不进行跨标签页同步：

- 新标签页启动时会读取当时的最佳成绩；
- 两个标签页同时游玩时，后一个写入最佳成绩的标签页会覆盖前一个；
- 因为每个标签页内部 `state.bests` 不会自动更新，理论上可能以较低分覆盖较高分；
- 对普通单人使用影响很小，但这是 0.1.0 的已知限制。

如需修复，可采用：

1. 监听 `window.addEventListener("storage", …)` 并合并最大分数；
2. 写入前重新读取当前存储，与内存值取最大值；
3. 或改用带同步能力的后端。

### 2.8 数据安全与隐私

| 项目 | 现状 |
| --- | --- |
| 传输 | 无网络传输 |
| 服务器日志 | 无 |
| Cookie | 无 |
| 埋点 / 分析 | 无 |
| 个人数据 | 不采集 |
| 好友关系 | 无 |
| 支付 | 无 |
| 用户生成内容 | 无 |
| 本地数据敏感度 | 低（仅游戏分数与尺寸偏好） |

本地数据可被同一浏览器用户或同源脚本读取、修改或删除。它们不用于身份认证，也不构成可信成绩证明。

## 3. 前端与“后端”的边界

当前所有游戏逻辑都在前端。若未来加入后端，推荐按下列边界拆分。

### 3.1 适合留在前端的职责

- 输入处理与方块动画；
- 当前对局状态；
- 本地即时计分；
- 本地最佳成绩；
- 离线游玩；
- 响应式 UI；
- 无障碍交互。

### 3.2 适合放到后端的职责

- 账号身份认证；
- 排行榜存储与排序；
- 跨设备成绩同步；
- 服务端对局校验 / 回放；
- 反作弊与限流；
- 运营数据统计；
- 隐私合规与数据删除接口。

### 3.3 直接改造点

如果后续接入后端，前端可优先改动以下函数：

| 函数 | 接入方式 |
| --- | --- |
| `readPreferences()` | 启动时读取本地缓存，并可异步拉取云端最佳成绩 |
| `savePreferences()` | 保留本地写入，同时排队提交最佳成绩到 API |
| `renderScore()` | 新纪录时触发可选的同步回调 |
| `showOverlay()` | 增加排行榜 / 登录 / 同步状态提示 |
| `startGame()` | 可接入服务端 runId / seed（高级防作弊） |

在离线优先策略下，建议：

1. 本地存储始终是即时可用的数据源；
2. 网络同步失败不影响游戏；
3. 云端数据和本地数据按“每种尺寸取最高分”合并；
4. 明确服务端校验失败时的提示与回退。

## 4. 可选后端设计（未实现）

> 本章为未来规划，不描述当前已存在的接口。若需要上线排行榜或云存档，请按此设计另行实现。

### 4.1 方案分级

| 方案 | 目标 | 复杂度 | 可信度 |
| --- | --- | --- | --- |
| A. 仅同步最佳成绩 | 跨设备记录 | 低 | 中 |
| B. 排行榜 + 服务端成绩校验 | 公开榜单 | 中 | 中高 |
| C. 服务端种子 + 完整对局回放 | 竞技级防作弊 | 高 | 高 |

当前游戏是离线随机、纯前端计分，没有服务端可信的运行环境，因此**任何直接提交的本地成绩都不应被视为权威竞技数据**。

### 4.2 推荐 API 草案（v1）

假设使用 HTTPS JSON API，版本前缀为 `/api/v1`。

认证建议使用 OAuth 2.0 / OIDC 或至少签名的会话 Token。若仅做匿名榜单，可使用匿名设备 ID + 限流，但可信度更低。

#### 启动对局（方案 C）

```http
POST /api/v1/runs
Authorization: Bearer <token>
Content-Type: application/json

{
  "size": 4,
  "clientVersion": "0.1.0"
}
```

响应示例：

```json
{
  "runId": "run_01J8Z3Y6Q8M9C4T2",
  "serverSeed": "b4d4e9b9a2f1...",
  "spawnAlgorithm": "sha256-counter-v1",
  "startedAt": "2026-10-20T08:00:00Z",
  "expiresAt": "2026-10-20T09:00:00Z"
}
```

客户端使用服务端种子生成新方块序列，能够被服务端独立复现。当前 0.1.0 使用浏览器 `Math.random()`，不具备此能力。

#### 提交成绩

```http
POST /api/v1/scores
Authorization: Bearer <token>
Content-Type: application/json
Idempotency-Key: 3e158e5b-05b2-4f2c-9a8e-9e7b4f2b0f01

{
  "runId": "run_01J8Z3Y6Q8M9C4T2",
  "size": 4,
  "score": 5632,
  "maxTile": 1024,
  "moves": 187,
  "durationMs": 642000,
  "clientVersion": "0.1.0",
  "moveSequence": ["L", "U", "L", "D", "…"]
}
```

简化方案（不使用 `runId` / 回放）可改为直接提交：

```json
{
  "size": 4,
  "score": 5632,
  "maxTile": 1024,
  "moves": 187,
  "durationMs": 642000,
  "clientVersion": "0.1.0"
}
```

响应示例：

```json
{
  "scoreId": "score_01J8Z4R8Y2K6W9M1",
  "accepted": true,
  "verified": true,
  "personalBest": 5632,
  "leaderboardRank": 42
}
```

#### 获取排行榜

```http
GET /api/v1/leaderboard?size=4&limit=20&offset=0
```

响应示例：

```json
{
  "size": 4,
  "period": "all-time",
  "total": 1842,
  "items": [
    {
      "rank": 1,
      "displayName": "山客",
      "score": 8244,
      "maxTile": 2048,
      "moves": 312,
      "achievedAt": "2026-10-01T12:31:00Z"
    }
  ],
  "me": {
    "rank": 42,
    "score": 5632
  }
}
```

#### 获取个人最佳成绩

```http
GET /api/v1/me/bests
Authorization: Bearer <token>
```

响应：

```json
{
  "bests": {
    "4": { "score": 5632, "maxTile": 1024, "achievedAt": "…" },
    "5": { "score": 2136, "maxTile": 1024, "achievedAt": "…" }
  }
}
```

#### 可选：撤销/删除数据

```http
DELETE /api/v1/me/scores
Authorization: Bearer <token>
```

用于用户主动清除云端记录，满足隐私删除需求。

### 4.3 数据模型草案

以下为 PostgreSQL 风格的参考结构，不是当前实际数据库。

#### `players`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid` PK | 玩家/设备匿名 ID |
| `display_name` | `varchar(40)` | 可选的榜单昵称 |
| `created_at` | `timestamptz` | 创建时间 |
| `last_seen_at` | `timestamptz` | 最近活动时间 |
| `deleted_at` | `timestamptz null` | 软删除 |

#### `runs`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid` PK | 对局会话 ID |
| `player_id` | `uuid` FK | 玩家 |
| `size` | `smallint` | 4 或 5 |
| `seed` | `text` | 服务端种子 |
| `status` | `varchar(16)` | started / finished / expired |
| `started_at` | `timestamptz` | 开始时间 |
| `finished_at` | `timestamptz` | 结束时间 |
| `verified` | `boolean` | 是否通过回放验证 |

#### `scores`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid` PK | 成绩 ID |
| `run_id` | `uuid` UNIQUE FK | 一局一条成绩 |
| `player_id` | `uuid` FK | 玩家 |
| `size` | `smallint` | 4 或 5 |
| `score` | `integer` | 总分 |
| `max_tile` | `integer` | 最大方块 |
| `moves` | `integer` | 有效手数 |
| `duration_ms` | `integer` | 时长 |
| `verified` | `boolean` | 是否验证 |
| `created_at` | `timestamptz` | 创建时间 |

建议索引：

```sql
CREATE INDEX idx_scores_size_score
  ON scores (size, score DESC, created_at ASC);

CREATE INDEX idx_scores_player_size
  ON scores (player_id, size, score DESC);
```

### 4.4 服务端校验规则

最低限度：

- `size` 只能是 4 或 5；
- `score`、`moves`、`durationMs` 必须是非负整数；
- `maxTile` 必须是大于等于 2 的 2 的幂；
- `moves` 上限应与棋盘尺寸和时长存在合理关系；
- 同一 `runId` 只能提交一次；
- `durationMs` 与对局开始时间一致；
- 客户端版本需在白名单中；
- 使用 `Idempotency-Key` 防止重试产生重复成绩。

若需要防作弊，应进行：

1. 服务端生成种子；
2. 客户端上报完整移动序列；
3. 服务端以相同匹配、生成逻辑重放；
4. 对比最终棋盘、最大方块、得分和手数；
5. 校验生成序列符合种子；
6. 对校验失败或时效过期的成绩拒绝上榜。

### 4.5 速率限制与防滥用

建议默认策略：

| 接口 | 建议限制 |
| --- | --- |
| `POST /runs` | 每玩家 / IP 每分钟 10 次 |
| `POST /scores` | 每玩家 / IP 每分钟 5 次 |
| `GET /leaderboard` | 每 IP 每分钟 60 次，允许缓存 |
| 身份认证接口 | 按认证服务策略 |

其他措施：

- 请求体大小限制（例如 32 KB）；
- 长度限制与类型校验；
- CORS 仅允许部署的游戏源；
- 内容安全与 TLS；
- 异常分数进入人工/自动审查队列；
- 清理过期 run（例如超过 2 小时未完成）；
- 对匿名流量按 IP 与设备指纹限流（注意隐私合规）。

### 4.6 认证与隐私选择

- 若只做跨设备同步：登录可选，优先 OIDC 或 passkey。
- 若公开排行榜：需要昵称与基础审核能力。
- 不要在未经明确同意的情况下采集不必要的设备信息。
- 提供数据导出 / 删除入口。
- 排行榜默认隐藏敏感信息，只展示昵称与成绩。
- 考虑未成年人隐私与当地法规。

### 4.7 部署草图

```text
                    HTTPS
Browser ──────────────────► CDN / Static Host
   │                              │
   │                              └── index.html
   │
   │  HTTPS + Bearer
   └──────────────────────► API Gateway / Nginx
                                  │
                                  ▼
                             App Server
                         (Node / Go / Python…)
                                  │
                                  ▼
                              PostgreSQL
                         scores / runs / players
```

静态前端和 API 可分开部署：

- 前端：Nginx、GitHub Pages、Netlify、Vercel 等；
- API：云服务器、容器、Serverless Function；
- 数据库：托管 PostgreSQL；
- 缓存：排行榜缓存可使用 Redis（可选）；
- 日志与监控：结构化日志、错误追踪、健康检查。

前端请求需处理：

- 认证过期；
- 网络离线；
- 超时与重试；
- 5xx 降级；
- 本地成绩与云端成绩合并；
- 服务端验证失败的提示；
- 隐私同意状态。

## 5. 可选改造路线

建议按阶段演进，而不是直接跳到复杂后端：

### 阶段 0：保持现状

- 单文件、本地成绩；
- 离线可玩；
- 适合个人项目和作品集。

### 阶段 1：轻量成绩同步

- 增加可选登录；
- 上传最佳成绩；
- 保留本地成绩作为离线副本；
- 排行榜可选关闭。

### 阶段 2：可信排行榜

- 服务端对局 seed；
- 完整对局回放；
- 成绩校验与限流；
- 前端增加生成序列的可确定性改造。

### 阶段 3：完整在线游戏服务

- 账户资料；
- 多端同步；
- 赛季/排行榜；
- 活动与运营工具；
- 数据删除与隐私合规流程。

当前 0.1.0 位于阶段 0。

- **当前版本没有后端**，是一款无需网络的单机前端游戏。
- 所有持久化仅限于浏览器本地的两项偏好数据。
- 当前架构足以满足个人游玩、分享和静态部署。
- 如未来需要排行榜或云同步，本文提供了可扩展的 API、数据表和反作弊方向，但必须另行实现并充分测试，不能把本地提交的成绩直接视为可信。
